# DockOff 详细设计

## 1. 目标和边界

DockOff 面向物理隔离或无网络 Linux 环境，提供 Docker Engine 和 Compose v2 的离线安装。联网构建阶段从受信任仓库收集 RPM 并生成单个 `tar.gz`；目标机由 Go 安装器检查环境、校验归档、安装组件、启动服务并验证结果。安装阶段不访问网络。

首版目标是 openEuler `22.03 (LTS-SP4)` 的 x86_64 和 aarch64，组件版本为 Docker Engine/CLI `28.5.2`、containerd.io `2.1.5` 和 Compose 插件 `2.40.3`。x86_64 已做安装及容器运行验证；aarch64 尚未在实机验证。业务镜像不属于安装包，后续由管理员单独传输并使用 `docker load`。

## 2. 独立目标模型

“操作系统发行版 + 发行版版本 + CPU 架构”定义一个独立支持目标。目标以 `internal/targets/profiles/<id>.json` 表示，目标 ID 唯一，例如：

| ID | OS ID | OS 版本 | Go 架构 | RPM 架构 |
| --- | --- | --- | --- | --- |
| `openeuler-22.03-lts-sp4-amd64` | `openEuler` | `22.03 (LTS-SP4)` | `amd64` | `x86_64` |
| `openeuler-22.03-lts-sp4-arm64` | `openEuler` | `22.03 (LTS-SP4)` | `arm64` | `aarch64` |

Profile 定义以下目标专属值：

- OS ID 和版本、Go 架构、RPM 原生架构。
- RPM 包格式、包管理器和 systemd 服务名。
- Docker Engine、Compose 版本与必须锁定的 RPM EVR。
- OS、更新和 Docker 仓库地址。
- 每把签名公钥对应的固定 SHA-256。

`targets.All` 加载并校验嵌入到二进制中的 JSON profile；`targets.Lookup` 按 ID 查询；`targets.Detect` 按 `/etc/os-release` 中的 ID、VERSION 和 `runtime.GOARCH` 精确匹配。未知组合会被拒绝，不会退化为仅检查发行版名称。

## 3. 命令和流程

### 3.1 `targets`

列出二进制内嵌的支持目标及其 OS、版本和架构，供构建操作选择目标 ID。

### 3.2 `prepare`

`prepare --target <id> --output <dir>` 在联网构建机生成一个目标 staging。构建机必须是 profile 对应的 Linux 发行版、版本和原生架构，并以 root 运行。建议使用干净系统，因为 DNF 根据构建机已安装包集求解依赖。

程序按 profile 选择 OS/更新仓库、RPM 架构、包版本和公钥散列。可用 `--docker-repo` 指定 Docker RPM 镜像；可用 `--docker-key` 提供 Docker 官方公钥文件。Docker 和 openEuler 公钥均先经过 SHA-256 校验，再导入构建机 RPM 数据库并验证 RPM 签名。此过程会修改构建机 RPM 信任库，推荐使用可丢弃的构建 VM。

DNF 临时配置只启用 profile 及命令行指定的仓库，关闭弱依赖，并以 `--downloadonly` 下载目标组件及依赖，不执行安装。目标依赖闭包受构建机基线影响，因此应在与最终目标机软件基线接近的干净系统构建。

Staging 目录结构：

```text
manifest.json
keys/<target-id>/docker.asc
keys/<target-id>/openeuler.asc
rpms/<target-id>/*.rpm
```

staging manifest 只含一个目标，记录来源 URL、RPM 元数据及除 manifest 自身外每个文件的 SHA-256。

### 3.3 `bundle`

`bundle --staging <dir> [--staging <dir> ...] --output <file.tar.gz>` 校验每个 staging 的 manifest、文件清单、目标包版本、公钥散列和 RPM 集合。每个 staging 必须恰好包含一个目标，同一目标不能重复添加。

程序根据每个 profile 的 `go_arch` 交叉编译 `install-<target-id>`，并把各目标 RPM 和 key 放入同一个暂存目录。最终 `manifest.json` 用 `targets` 对象记录各目标的 RPM 元数据及来源，`files` 记录共享 bundle 内所有文件的 SHA-256。bundle 文件校验清单按目标 ID 隔离 RPM 与公钥路径：

```text
manifest.json
keys/<target-id>/*.asc
rpms/<target-id>/*.rpm
install-<target-id>
```

未传入 staging 的目标不会出现在包中。生成后再次检查完整归档目录，再写出 gzip 压缩 tar，并打印整个归档 SHA-256。当前不对 manifest 或 tar.gz 做项目私钥签名；传输时应独立记录并核对归档散列。

### 3.4 `install`

用户在目标机解压 tar.gz 后，以 root 执行 `install-<target-id> install --bundle <dir>`。安装器先检测目标机 profile，再要求 bundle 含有完全匹配的 target ID。安装步骤如下：

1. 识别 `/etc/os-release` 的发行版 ID、版本和安装器架构，拒绝不支持或不匹配的系统。
2. 检查 root、profile 声明的包管理工具、RPM 工具、systemd 和磁盘空间，并获取互斥锁。
3. 将过程日志写入 `/var/log/dockoff/`。
4. 校验 manifest、全量文件清单和 SHA-256，校验目标公钥散列、RPM 签名及 RPM 元数据。
5. 检查已有 Docker/容器运行时软件冲突；已有同名目标包只有版本完全匹配时才允许继续。
6. 使用临时 DNF 配置、空仓库目录、`--disablerepo=*` 和 `--noplugins`，对本地 RPM 路径运行 `--assumeno` 依赖预检。
7. 校验通过后，将 profile 中的公钥导入系统 RPM 信任库，通过本地 RPM 文件执行 DNF 安装。
8. 依 profile 的 systemd 服务名 enable/start 并检查 active/enabled。
9. 校验已安装 RPM EVR、Docker daemon Engine 版本、Compose 版本和 `docker info`。

`install --check` 执行到离线依赖预检后退出，不导入系统公钥、不安装 RPM、不更改服务状态。

### 3.5 离线保证

目标机执行 DNF 时显式禁用所有 repo 和插件，参数只包含归档中的 RPM 绝对路径。签名校验、公钥导入、systemd 操作和 Docker 验收均为本地操作。安装器不执行 `docker pull`，归档也不含业务镜像。

## 4. 增加新目标的步骤

1. 为一个确定的发行版、版本和架构新增 `internal/targets/profiles/<target-id>.json`。ID 应明确包含发行版、版本和架构，且不与现有 ID 冲突。
2. 填写准确的 `/etc/os-release` `ID` 和 `VERSION` 值，并填写 Go 架构与 RPM 架构的对应值。
3. 确认包管理后端、Docker 服务名、OS/updates/Docker 仓库地址、目标组件版本及每个必须锁定包的 epoch/version/release。
4. 固定可信公钥的 SHA-256；验证密钥来源和 RPM 签名。密钥轮换应显式更新 profile 和变更记录。
5. 在匹配的联网原生构建机运行 `dockoff prepare --target <id>`，检查完整依赖闭包、包架构、RPM EVR 和签名。
6. 在相同系统版本上使用 `install --check` 验证离线依赖闭包；再测试安装、重跑、服务启动及 Docker/Compose 版本。
7. 用一个或多个 staging 运行 `bundle`，检查归档只含预期 targets，并在目标架构上完成实际验证后再标记为正式支持。
8. 更新中英文支持矩阵、测试状态和本文档。

增加 RPM 系发行版通常可以沿用现有安装后端，但仍需单独 profile 和系统验证。增加 DEB/APK 或非 systemd 系统时，需要先扩展安装器的包管理或服务管理抽象，再加入 profile；仅添加 JSON 不足以声称支持。

## 5. 兼容策略和风险

已有包版本不匹配、发现冲突包、依赖闭包不全、签名无效、系统版本或架构不匹配时停止。安装器不自动卸载冲突组件、不降级包、不迁移 Docker 数据目录。正式 RPM 事务中断时不保证完全回滚；应查看 `/var/log/dockoff/` 和 DNF 历史。

profile 中组件 RPM pin 是必须出现且 EVR 精确匹配的包；额外系统依赖由构建 DNF 解析并记录在 manifest，目标机不重新访问仓库求解。完整离线安装依赖目标机基线与联网构建机求解结果相容。

## 6. 代码目录职责

```text
cmd/dockoff/main.go        命令分发与 targets 列表
cmd/dockoff/build.go       profile 驱动的 RPM 准备、归档和安装器交叉编译
cmd/dockoff/install.go     目标检测、离线安装、服务启动和验收
cmd/dockoff/common.go      manifest、文件校验、RPM 元数据和主机识别
cmd/dockoff/platform_*.go  Linux 安装锁和磁盘检查
internal/targets/          profile 类型、加载、查找和目标机匹配
internal/targets/profiles/  嵌入的每目标 JSON 配置
```

- aarch64：有 profile 和交叉编译路径，尚未做实机 RPM 安装或容器验证。
- 新目标流程仍需在每个目标 OS/版本/架构上进行 staging、离线预检和安装验证；添加 profile 本身不代表该目标已经测试通过。
